## 1. Why

The takeoff rpm/MAP cycle was found by a loop, not by a statistic: cut every full-power segment, notice the MAP lockstep, read the OM engine deck, form the limit-cycle hypothesis, test it against altitude, eliminate the clutch-slip and ECU-limiter alternatives, write it up so the manufacturer recognised it in one email. The statistics were twenty-minute scripts; the loop was Claude's, steered by the owner. Spec 06 built a UI around the scripts and left the loop out — which is why it kept needing another level of screens (v0.6, withdrawn).

The app's job is therefore not to reproduce the loop in forms, but to make a good investigator possible: give the user's own AI an instrument (tools), a bench (code against the data), the literature (the OM and the aircraft's configuration), a way to keep evidence (a notebook), and a reason to look (an inbox). The pilot asks in words; the investigator works; the study appears in EIS.

## 2. The model

### 2.1 Two tiers of user

| Tier | Runs | Gets |
|---|---|---|
| **Casual** | the website (browser mode, Pyodide, nothing installed) | Flights, Trends, Journal, the manual Research tools (Spec 06). Logs never leave the browser. No investigations. |
| **Advanced** | the **Claude Desktop extension**, one install, which carries the EIS engine and serves the EIS pages locally | everything above, plus investigations: their own Claude connected to EIS through MCP |

The website keeps its workspace in browser storage; the extension keeps its on disk. Both read the same log folders; decisions move between them by workspace export/import (Spec 02 §7). A smoother hand-off is a later concern.

**What the code Claude runs on your computer can and can't do.** On a Mac, macOS itself fences it in: it can't reach the internet, start other programs, or change any file outside its own study folder. That fence exists only on a Mac, and the macOS tool it uses (`sandbox-exec`) is one Apple has deprecated, though it still works today; on Windows and Linux only EIS's own, weaker check applies. On every computer the code can *read* any file you can, and what it reads can end up in your conversation with Claude.

### 2.2 Where the pieces run

On the user's computer: the **EIS engine** (Python, the same one Spec 04 describes), with two front doors — the local web server for the browser tab, and the **MCP server** for Claude Desktop. Both see the same workspace: a notebook cell written by the investigator appears in the browser's Research page; a filter pinned in the browser is seen by the investigator's next tool call. Claude Desktop launches the MCP server from the extension bundle; the only network traffic is Claude's own conversation with Anthropic. The AI never reads log files; it calls tools.

### 2.3 Where the user works

The user *looks* in EIS — the Flight view with the Signal strips — and marks what looks odd (*Mark for Claude*, D16); the user *asks* in the Claude app — *"the climb after my touch-and-go at KBLI on Oct 24 felt like a surge; look into it"* — and steers there. The study forms in EIS as the investigator writes it. Claude is where the user thinks; EIS is the instrument and the record. There is no chat box inside EIS: that would mean EIS hosting the AI loop with a key, a service the owner will not run, and a worse Claude than the real one (no Projects, memory, attachments or skills). The standing context every investigation starts with is what the `guide` tool returns (D13): the method, the aircraft record, the owner's notes, and where the documents are. A Claude Project for the aircraft is a convenience, not a requirement.

### 2.4 What the MCP server exposes (layers)

1. **Raw material** — flights, channels and series, phases, events, the cached per-flight analysis, fleet metrics, baselines and trends.
2. **Research instrument** — Spec 06's operations: presets, slices, descriptors, the four questions, samples, `analyze_signal`, `compare_rows`, studies.
3. **Bench** — a code tool: run Python against the workspace in the local engine process (scope: D3).
4. **Context** — the engine profile, the aircraft record and the owner's notes, prior studies and Journal, and the documents in the folders the owner named for the aircraft (the OM stays the user's copy, read in place; Spec 06 §1 constraint).
5. **Record** — notebook-writing tools: append a cell, attach a figure or table, finish a study; the inbox (D5).

### 2.5 A study is a notebook

An investigation is a Jupyter notebook (`.ipynb`, D12): narrative cells, code cells with their outputs, figures, tables and log-view cells — authored by the investigator through tools, rendered by EIS in the Research view and by any Jupyter front end, saved in the workspace, re-runnable (on new flights, after a change, on another owner's workspace), shareable as the notebook itself. Hand studies (Spec 06) keep their own document. The model case's write-up — question, what was looked at, what was found, what it means, what to do, every number traceable — is what a finished notebook should read like; the `guide` tool (D13) says so to the investigator.

### 2.6 Proactive: detection decides *when*, the AI decides *what it means*

The AI does not read every flight. When the inbox is next read after an import (or on demand) EIS runs its deterministic, recurrence-gated scan on the preset slices (Spec 06 §14.1): a pattern in N of M recent slices, a descriptor shifted against the fleet reference, a physics flag such as a prominent period in governed rpm. Candidates go to a **Research inbox**, never onto flight cards, each with its evidence table. The user's AI investigates on request (*"look into this"*) or on a cadence the user sets, which Claude's own scheduling can drive. An investigation ends as a study in the inbox; "nothing here" is a legitimate outcome and is recorded so a candidate is not re-investigated. A single odd flight is the Flight view's job, not the inbox's. Details: D5.

### 2.7 Trust and privacy

Every claim in a notebook traces to a tool result, a code cell's output, or a cited document, or is labelled a hypothesis; the pilot sees the code. No verdict words without their reference (Spec 06 §8 applies to notebooks). The engine runs no AI and stores nothing on anyone's behalf; the user's Claude account carries the conversation. Only what the investigator asked for leaves the machine, in Claude's conversation; raw logs never do unless the user attaches one.

## 4. The MCP server (D1, D3, D7)

### 4.1 Transport and process
A third front door to the host (Spec 04): `slingology-eis mcp` runs the MCP server over stdio in the same process as the engine and, in the extension, the web server (§7). Every tool is a thin façade over a Spec 01 host operation or a composition of them; results are the operations' JSON, trimmed to summaries where §4.2 says so. The host is unchanged except for the new operations §4.3 lists. Capability gating: the surface is present only when a workspace is open; otherwise every tool answers *no workspace yet — open the EIS pages at 127.0.0.1:8420*. Which workspace (D10): the aircraft named in the extension's configuration (or the registry's only aircraft) and its workspace; with several workspaces for that aircraft, the most recently opened, and `workspaces_list` / `workspace_use` to change for the conversation.

A rule is a preset id, `"phase:CLIMB"` or a §5.1 rule object. The value of a cell's last expression is an output, as in Jupyter. Each cell starts afresh (S3).
- *Enforcement*: a worker process per cell (S1) with a minimal environment, started in its own process group (the wall-clock cap kills the group), a watchdog on resident memory, and two layers (S2): (1) a PEP 578 audit hook installed before the cell runs — refuses socket, ctypes, `subprocess`/`os.system`/`os.exec*`/`posix_spawn`/`fork`/`kill`, `http.client`, `urllib` and `webbrowser` events, a second audit hook, and any open-for-writing, remove, rename, mkdir, chmod or similar outside `files/`; `_posixsubprocess.fork_exec` (which raises no audit event) is replaced and fresh loads of `_posixsubprocess`, `_ctypes`, `_socket`, `_ssl` refused; (2) on macOS, the kernel's sandbox profile: network denied, process fork and exec denied (but the interpreter's own start), file writes denied outside `files/`, the bench's scratch and the matplotlib cache.
- **Plainly: the kernel boundary is macOS-only; reads are not confined; `sandbox-exec` is deprecated by Apple.** On macOS the kernel refuses a cell's network access, new processes and writes outside its folders even when the cell has defeated the audit hook. On Linux and Windows there is no kernel boundary — the audit hook is the only check, and it stops mistakes, not code written to escape. On every platform a cell can read any file the user can. The macOS layer uses `sandbox-exec`, which Apple has deprecated (it still works on current macOS); if Apple removes it, the bench falls back to the hook alone and the spec must say what replaces it.
- *What it cannot enforce*: **reads are not confined** — a cell can read any file the user can, and what it prints goes to the investigator (Claude) and into the study; **on Linux and Windows the hook is the only layer**, and the hook is not a security boundary: Python code in the same interpreter can reach and disable it (demonstrated in the tests, where on macOS the kernel layer then refuses); the memory cap samples resident size, so a sudden allocation can overshoot before the process is stopped; CPU use within the wall clock is not limited; the envelope guards against mistakes and casual misuse in code the user can read before approving, not against code written to escape on a platform without the kernel layer.

### 5.4 Running outside EIS (D14)
The setup cell binds `eis` in any Jupyter kernel that has `slingology-eis[investigations]` installed (`.venv/bin/python -m ipykernel install --user --name slingology-eis` once). `eis.open` reads the registry's data root (or `data_root=`), opens the workspace, and gives the same functions as the bench, including `eis.logview` (which outputs the SVG and the JSON; JupyterLab shows the SVG). Nothing is sandboxed: the kernel is the user's. Cells run outside EIS do not update the notebook EIS holds unless the user saves the file in place — the notebook *is* the file under `studies/<id>/`, so saving in JupyterLab is enough; the Research page then shows the outputs marked *ran elsewhere* until a bench re-run (D4 semantics) or the user accepts them as they are (`study_accept` with `source: "external"`).


### 5.5 What a notebook says about itself (v1.1)
Computed by the engine when a notebook is created, appended to or finished, stored in notebook metadata (`slingology.card`) and returned by `list_studies` / `studies_list`, so the page computes nothing:

- `origin`: `marks` (created with `question_id`), `candidate` (created with `inbox_candidate`), `asked` (neither), `imported`;
- `channels`: the union of channels in its log-view payloads and in the tests its code ran (the `eis` library records them as the cell runs);
- `flights` (count) and `date_span` (first–last flight date, local) from the cells' `ran.flights` union;
- `evidence`: counts of log views, figures and tables among the outputs; `tests`: the distinct Spec 06 tests the cells ran;
- `outputs`: `current` · `pending` · `elsewhere`, as the Research page already derives per cell, reduced to one word;
- `resolution`: the resolution `study_finish` gave its inbox item or question, if any;
- `tags`: from `study_finish tags` (≤ 5 short words; free text). The guide asks Claude for two or three topic words — what the notebook is about, not what it found.

The fields are derived data and are recomputed on import; an older notebook without them gets them on first load.

## 6. The inbox and cadence (D5)

- **Scan** (`inbox_scan`): when the inbox is next read after an import, and on demand (S7). ## 7. The Claude Desktop extension (D6)

As built in Session F. The mechanics were checked on Nov 15 2026 against the MCP Bundle documentation (the `modelcontextprotocol/mcpb` repository's `MANIFEST.md` and `CLI.md`, CLI `@anthropic-ai/mcpb` 2.1.2) and Claude's *Build a desktop extension with MCPB* page:

- **Format.** An MCP Bundle (`.mcpb`, formerly `.dxt`) is a zip with `manifest.json` at its root, made with `mcpb pack` (which validates the manifest first). `manifest_version` 0.3. Server types are `node` (Node.js ships with Claude Desktop, and is the recommended language), `python` (every dependency bundled, under `server/lib` or a venv, run by a Python the user has), `uv` (the host installs the dependencies from `pyproject.toml`; the manifest's v0.4) and `binary`. EIS uses **`binary`**: the command is the bundled Python, so nothing depends on what the user has installed and the compiled stack (numpy, scipy, matplotlib) is the build's. `mcp_config` holds `command`, `args` and `env`, with substitutions `${__dirname}` (the unpacked extension), `${HOME}` and the like, and `${user_config.KEY}`, where a `multiple` setting expands to one argument per value.
- **User configuration.** Declared under `user_config`, with types `string`, `number`, `boolean`, `directory` and `file`, and options `required`, `default`, `multiple` (directory and file only) and `sensitive`. Desktop draws the settings form from it. EIS declares three settings, all optional, so a first run needs none:
  - `data_root` (directory): empty means the one the pages use, Spec 02 §5.8.1.
  - `aircraft` (string): empty means the only aircraft, else the most recently opened (D10).
  - `log_folders` (directory, multiple).
- **Install.** The user double-clicks the `.mcpb`, drags it onto the Claude Desktop window, or uses Settings → Extensions → Advanced settings → *Install Extension…*. Each opens Desktop's install view (details, settings, install). Installation is per user. The Claude directory no longer lists extension bundles, so distribution is the release asset.
- **Signing.** `mcpb sign` signs with a PEM certificate and key (`--self-signed` for development), and `mcpb verify` / `info` show a bundle's status. The documentation doesn't say how Desktop treats an unsigned bundle. Developer write-ups and user reports describe a warning with a way to install anyway, and some report Desktop builds where a local `.mcpb` install fails silently. **Signing is deferred.** The install walkthrough tells the user to expect the warning, and the owner's first install is the check on the current Desktop build.

The bundle and process:

- **Bundle.** One per architecture, `slingology-eis-<version>-macos-arm64.mcpb` and `…-macos-x86_64.mcpb` (Windows later). Each holds:
  - a standalone CPython 3.12 (python-build-standalone; release and checksum pinned);
  - the engine wheel with the `investigations` extra installed, the wheel carrying the built UI;
  - the manifest and the icon.

  The bundle is about 100 MB packed. No bytecode ships (it would add 40 MB): the first start writes it into the extension's folder, about 9 s, and later starts take 0.2 s. Built by `scripts/build_extension.py` on the target architecture. CI builds it on `macos-15` and `macos-15-intel` after the main job, keeps the bundles as artifacts and attaches them to the release on a `v*` tag. Developer note: `docs/extension-build.md`.
- **Process.** Desktop runs `python3 -I -m slingology_eis.investigations.extension` with the configuration, which becomes `slingology-eis mcp serve --serve --port 8420 --log-file` plus the aircraft and folders. That is one process: MCP on stdio, and the EIS pages on 127.0.0.1:8420 on a thread. It ends when Desktop closes the connection. If 8420 is taken (`slingology-eis serve` already running), the pages aren't served from this process, a line in the log says so, and the tools carry on. Messages go to Desktop's MCP log and to `cache/mcp.log` under the data root (started afresh past 2 MB).
- **Two processes per start (Claude Desktop's).** Desktop starts the command twice on each launch: once for the chat's connection (*Launching MCP Server*) and once from its `LocalMcpServerManager` (*Connecting to …*, which negotiates its own protocol version, lists the tools and announces them to Desktop's `localMcpBridge`). Both appear in `main.log` within a second of each other, and both write to the one per-server log (`mcp-server-SlingologyEIS.log`), so its banner shows twice. Nothing in the extension starts a second server. The first process takes port 8420; the second finds it taken and serves the tools only. Both link the configured log folders (adding a folder twice is a no-op) and both append to `cache/mcp.log`, whose lines carry the process id so the two can be told apart (F15).
- **Data.** The server-mode data root, shared with a pip install, so there is one registry. The configured log folders are linked to the workspace the tools open as soon as one exists: added, never removed (the pages own the list). First run: the tools answer *no workspace yet*, and the pages show the first-workspace flow.
- **Install for the user.** The walkthrough *Install the extension* covers which file to download for the Mac, the unsigned warning, the settings and the first run. The website's inbox links to it where there is no bench.

**As built (Session H).** The extension's server is the one D17 posts to: `GET /eis/probe` and `POST /eis/move-workspace` are open to the website's origin and no other route is (SH1–SH2). Its first-run page (the first-workspace page, D18) says *Been using the website? Open it and press Move my workspace.*; so does the install walkthrough's first-run step.

## 10. Relationship to other specs
